**Release date:** 2026-07-17
**Scope:** Hotfix for a v1.7.0 regression — "Show basket" opened an empty window. No other changes.

## What was broken

v1.7.0's hardening pass bound the dialog window classes to the DLL module (`g_hModule`) so their WndProcs can't outlive the DLL. The splitter child window, however, was still created with `GetModuleHandle(NULL)` — the `explorer.exe` instance handle. Application-local window classes are resolved by the **(class name, hInstance)** pair, so `CreateWindowExW` no longer found the `CopyBasketSplitter` class and returned `NULL`.

`LayoutControls` positions all five child controls through a single `BeginDeferWindowPos`/`EndDeferWindowPos` batch. The `NULL` splitter handle made that chain fail, so **no control was ever positioned**: ListView, TreeView, buttons and status bar all stayed at 0×0 pixels. The dialog window itself appeared (its own class/instance pair was correct) — visibly empty, with the basket contents loaded but invisible.

## The fix

Every child `CreateWindowExW` in `BasketDialog` and `SettingsDialog` now passes `g_hModule`, matching the class registration. For the system classes (ListView, TreeView, BUTTON, status bar) this is functionally neutral; for the app-local splitter class it is required. A comment at the splitter creation site now documents the constraint.

Verified with a test host that loads the dialog sources as a DLL — the mismatch only manifests when `g_hModule != GetModuleHandle(NULL)`, so an EXE-based test would hide it:

| | Splitter | Items loaded | ListView size |
|---|---|---|---|
| v1.7.0 | `NULL` | 7 | 0×0 (invisible) |
| v1.7.5 | created | 7 | 1024×288 (visible) |
