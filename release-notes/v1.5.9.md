# CopyBasket v1.5.9

**Release date:** 2026-05-16
**Scope:** Basket-dialog TreeView — two bug fixes, no other functional changes.

## Highlights

Both fixes are in the **TreeView detail panel** of the basket dialog (the read-only pane that shows the contents of the selected basket entry). The viewer used to be unusable for two reasons:

1. Selecting a folder with a deep or cyclic subtree could hang or crash the dialog.
2. Once that was fixed, the first level of children appeared **twice** for every selected folder.

v1.5.9 fixes both.

---

## 🟢 Lazy-loading TreeView

The TreeView used to walk the **entire** subtree of the selected basket entry up-front via a recursive `AddTreeNodes`. For shallow trees this was fine; for deep trees (and especially for paths containing reparse points like a user profile's legacy `Application Data` → `AppData\Roaming` junction) the dialog hung indefinitely or crashed when the recursion ran into a cycle.

The TreeView now loads **one level at a time**:

| Aspect | Before | After |
|---|---|---|
| Initial population | Recursive `AddTreeNodes` walked the full subtree | `PopulateChildren` loads **one level**; root is pre-expanded so users still see contents immediately |
| Deeper levels | Already in memory | Loaded on `TVN_ITEMEXPANDINGW` when the user clicks the expand arrow |
| Per-node storage | None | Full path on the heap via `lParam` (freed in `TVN_DELETEITEMW`) |
| Reparse points | Traversed → potential cycle / hang | `cChildren=0`, no expand arrow, never traversed |
| Empty directories on expand | Arrow stayed visible (misleading) | `cChildren` reset to 0 so the arrow disappears |

`InsertTreeNode(hParent, name, fullPath, icon, isDirectory, isReparsePoint)` decides per node whether to show the expand arrow and whether to attach a path; `PopulateChildren` does exactly one `FindFirstFileW`/`FindNextFileW` pass. Directories first, then files, stable order, icons via the existing `GetSysIconIndex` helper. Flicker is contained with `WM_SETREDRAW` FALSE/TRUE around the populate block.

## 🟢 No more duplicate first-level entries

After the lazy-load refactor, selecting a folder showed every direct child **twice**. The root cause was a subtle interaction between the eager-load of level 1 and the lazy-load handler:

`PopulateTreeFromPath` populates the root's children itself (so the user doesn't have to click to see them) and then calls `TreeView_Expand(hRoot, TVE_EXPAND)`. The expand fires `TVN_ITEMEXPANDINGW` while `TVIS_EXPANDEDONCE` is still clear — that flag is only set **after** the first expand completes. The lazy-load handler's guard was `!(state & TVIS_EXPANDEDONCE)`, so it dutifully populated the children a second time.

| Before | After | Why |
|---|---|---|
| `!(ntv->itemNew.state & TVIS_EXPANDEDONCE)` | `!TreeView_GetChild(nm->hwndFrom, ntv->itemNew.hItem)` | The check now asks the question we actually mean ("does this node already have children?") rather than relying on a system flag that's set at the wrong moment in the eager-load → expand sequence |

The new guard is also self-explanatory at the call site: if the node has no children, load them; otherwise, leave them alone (collapse + re-expand keeps the existing children, no rescan needed).
