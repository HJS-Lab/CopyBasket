**Release date:** 2026-05-15
**Scope:** CB-CMT (the portable Context Menu Tool) — DLL is unchanged.

## Highlights

This is a **CB-CMT-only** release. The shell-extension DLL (`CopyBasket_x64.dll` / `CopyBasket_x86.dll`) is byte-for-byte equivalent to v1.5.6 — only the portable `CB-CMT.exe` carries new behavior. Users who installed via the NSIS installer get nothing new; only the portable workflow benefits.

Two behavior changes plus an internal cleanup of `regsvr Tool/CopyBasketContextMenu/main.cpp`.

---

## 🟢 Detect partial registration

`CB-CMT.exe` used to inspect a single registry key (`HKLM\SOFTWARE\Classes\*\shellex\ContextMenuHandlers\CopyBasket`) to decide whether the DLL was registered. The DLL actually writes **three** keys during `DllRegisterServer`:

- `HKLM\SOFTWARE\Classes\*\shellex\ContextMenuHandlers\CopyBasket`
- `HKLM\SOFTWARE\Classes\Directory\shellex\ContextMenuHandlers\CopyBasket`
- `HKLM\SOFTWARE\Classes\Directory\Background\shellex\ContextMenuHandlers\CopyBasket`

If a previous uninstall left the system in a partial state (e.g. only one or two of the three keys present), the tool **lied**: it reported "fully registered" and pre-selected **Deactivate**, even though right-clicking files would only sometimes show the menu.

Now `IsCopyBasketFullyRegistered()` requires **all three** keys. Any missing key flips the default to **Activate**, so the user can complete a broken registration with one click. The list `REG_PATHS[]` in `main.cpp` mirrors `SHELLEX_KEYS[]` in `CopyBasket.cpp` — extending the shell locations means updating both.

## 🟢 Retry-on-error: dialog stays open after failure

Previously the OK button could close the dialog even on failure (depending on the failure path), forcing the user to relaunch the tool. The behavior was inconsistent across the three error paths:

| Failure | Old behavior | New behavior |
|---|---|---|
| `CopyBasket.dll` not found in EXE directory | closed dialog | **stays open** |
| `ShellExecuteEx` failed / no process started | stayed open | **stays open** |
| `regsvr32` exited with code ≠ 0 | closed dialog | **stays open** |
| All checks passed, registration succeeded | closed dialog | closed dialog |

Only success calls `EndDialog`. Users can fix the underlying problem (drop the DLL next to the EXE, accept the UAC prompt, etc.) and hit OK again without re-launching.

## 🛠 Internal refactor of `main.cpp`

No behavior change beyond the two items above. Mechanical cleanups:

- **108-line `IDOK` case split** into three helpers: `BuildDllPath(out, cch)`, `RunRegsvr32(dllPath, activate, outLaunched)`, `OnOkClicked(hDlg)`. The `WM_COMMAND/IDOK` branch is now a one-liner.
- **User-visible message strings hoisted** to file-scope `static const wchar_t*` constants near the other config (single source of truth — easier to edit, no more inline literals scattered through the OK handler).
- **Bounded formatting** with `StringCchPrintfW` / `StringCchCopyW` from `<strsafe.h>` everywhere; `wsprintfW` removed (the legacy API had no length checks).
- **`IsCopyBasketRegistered`** (now `IsCopyBasketFullyRegistered`) marked `static` for consistency with sibling helpers.
