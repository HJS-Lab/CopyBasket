**Release date:** 2026-05-22
**Scope:** Single concurrency fix in the file-operation layer, no other functional changes.

## Highlights

A second right-click on **"Copy basket here"**, **"Move basket here"**, **"Copy to..."**, or **"Move to..."** while an operation was still running used to launch a second `IFileOperation` thread. Both threads then competed for the same source files **and** for the single incident log — with two visible failure modes:

1. The first incident's `operations.log` was clobbered by the second op (so the user lost the diagnostic for the operation they actually cared about).
2. If the two threads tried to open `operations.log` at the *exact* same moment, the second `CreateFileW` (`CREATE_ALWAYS` + exclusive share) silently returned `INVALID_HANDLE_VALUE` — `WriteOperationLog` then returned an empty path and the abort dialog was skipped entirely (`if (!logPath.empty())` guard). The user got no feedback that anything went wrong.

v1.6.0 prevents the second operation from starting at all.

---

## 🟢 Single-op-in-flight guard

A new process-local flag, `g_fileOpInFlight` (`volatile LONG`), is claimed atomically when `LaunchFileOp` spins up the background thread and released only when that thread fully exits.

| Aspect | Before | After |
|---|---|---|
| Two right-clicks during an op | Two `_beginthreadex` workers run simultaneously | Second click is rejected before the picker opens |
| User feedback on rejection | None — second op ran silently and may have failed silently | Localized `MessageBoxW` ("Operation in progress" / "Vorgang läuft") anchored to `lpcmi->hwnd` |
| `operations.log` | Could be clobbered or fail to open under contention | Only one writer ever exists at a time |
| Abort dialog | Could be hidden when the second op's `CreateFileW` lost the race | Cannot occur — the second op is gone before any IO happens |

## 🟢 Two check points

`HandleFileOp` (`ShellExt.cpp`) checks `FileOps::IsBusy()` **before** opening `BrowseForFolder`, so the user is never asked to pick a destination for an operation that will be discarded. This is the friendly UX path.

`LaunchFileOp` then re-checks atomically via `InterlockedCompareExchange(&g_fileOpInFlight, 1, 0)`. This is the race-tight defense if two right-clicks somehow slip through the `IsBusy()` window — `LaunchFileOp` simply returns without scheduling work, leaving the existing op untouched.

## 🟢 Slot held across the abort dialog

The slot is **not** released when `PerformOperations` returns — it's released in `FileOpThreadProc` after `ExecuteFileOpCOM` returns in full. If the operation produced an incident and is currently showing the **"Open log / Close"** TaskDialog, the slot stays claimed and a new operation cannot start. This is intentional: the user must acknowledge the incident before queueing another job, otherwise a second operation could trample the very log file the user is about to open.

| Stage in `FileOpThreadProc` | Slot state |
|---|---|
| `_beginthreadex` started | Claimed |
| Inside `PerformOperations` | Claimed |
| Showing abort dialog (`ShowAbortDialog`) | Claimed |
| Dialog dismissed, `ExecuteFileOpCOM` returns | Claimed |
| `InterlockedExchange(&g_fileOpInFlight, 0)` | Released |
| `InterlockedDecrement(&g_cRef)` | Released |

Releasing **before** the DLL refcount drop means that a follow-up op triggered indirectly from the dialog (e.g. via `ShellExecuteW` in the "Open log" branch) is not falsely rejected as busy.

## 🟢 Scope: process-local

The flag is a single `static volatile LONG` in `FileOps.cpp`, not a kernel object — process-local by design. With Explorer's default single-process model this is sufficient (all right-clicks from any Explorer window in the user's session share the same DLL instance). Users who enable **"Open folder windows in a separate process"** get one independent slot per Explorer process; cross-process serialization would require a named mutex similar to `BasketLock` and is an acceptable trade-off versus the added complexity.
